# Requirements compliance matrix

This matrix maps the technical challenge to code, tests and reproducible commands. Runtime evidence must be regenerated on the delivery machine after any infrastructure change; `make verify-delivery` does that without inventing results.

| Requirement | Implementation | Verification / evidence |
|---|---|---|
| Full Laravel stack in Docker Compose | `docker-compose.yml`, Nginx, PHP-FPM, MySQL, Redis, Horizon, Scheduler | `docker compose up -d --build`; API entrypoint automatically migrates/seeds |
| Separate notification service in same Compose | `notification-provider/`, service hostname `notification-provider` | `curl localhost:8081/health`, `make provider-test` |
| Internal container communication, no localhost/IP | `NOTIFICATION_PROVIDER_URL=http://notification-provider:8080` | `docker/app.env`, HTTP client config |
| One command migrations + seeds | API bootstrap entrypoint | Happens automatically during `docker compose up`; `make setup` is equivalent |
| Users / roles / auth | Sanctum, `UserRole`, policies | Phase 1 tests |
| Organizer creates event and seat map | Event/Seat controllers + ownership policies | Phase 1 tests; API docs |
| Buyer lists available seats | `SeatController@index` | reservation tests |
| Ownership | Event/Reservation/Order/Ticket policies and scoped lists | Phase 1/3/5 tests |
| Temporary reservations | `expires_at`, `reserved_until`, scheduler cleanup | `ReserveSeatsTest::test_expiration_command_releases_seat` |
| Correct even before cleanup runs | expired hold is reclaimable inside locked reservation transaction | expired-reclaim tests |
| No double reservation / sale | deterministic `SELECT ... FOR UPDATE`, short MySQL transaction | `make load-test`: 50 requests / 10 seats, confirms the 10 winners, then SQL-checks zero duplicate reservations/sales |
| Confirm purchase and generate ticket/QR | `ConfirmPurchase`, opaque UUID + `qr_payload` | Phase 3 confirm tests |
| CPF stored on ticket with LGPD care | encrypted cast, masked API, excluded from Outbox/provider/audit | Phase 3 tests |
| No duplicate ticket for same purchase | unique `orders.reservation_id`, lock + idempotent confirm | confirm idempotency test |
| Real HTTP notification | `HttpNotificationProvider` from Horizon job | provider/resilience scripts + notification tests |
| Slow / error / duplicate / down simulation | provider admin mode endpoint | `make provider-test` |
| No silent loss after repeated failures | durable `NotificationDelivery`, retries/backoff, failed state, retry command | notification tests, `notifications:retry-failed` |
| Provider outage must not block purchases | no provider HTTP in checkout transaction | `make resilience-test` |
| Communication problem observable | Horizon, Pulse, delivery state, `/api/ops/metrics` | local dashboards + endpoints |
| Cancel confirmed purchase and release seat | `CancelOrder` transaction | cancellation test |
| Automated tests phases 1-3 | `api/tests/Feature` | `make test` writes `docs/evidence/phpunit.txt` |
| Mandatory load test | k6 50 VUs, each of 10 seats has 5 contenders | `make load-test` writes `docs/evidence/seat-contention.txt` |
| ADR/RFC 1-2 pages | `docs/ADR-002-resilience-scale.pdf` | verified 2-page PDF |
| ADR alternatives/trade-offs | sync HTTP, no-Outbox job, exactly-once, Kafka alternatives | ADR section |
| 10x/100x/multiple instances | ADR + README | documented architecture section |
| Product-rule improvement | virtual queue + per-buyer limit + short checkout window | ADR + DECISIONS |
| Phase 5: report with ~200k tickets | `ReportBenchmarkSeeder`, SQL aggregation | `make phase5-seed`, `make benchmark-report` |
| Phase 5: search with thousands | 10k-event seed, indexed prefix/date search | `SearchBenchmarkSeeder`, Phase 5 test, `make benchmark-search` |
| Search unavailable behavior | explicit 503 only for search | Phase 5 test |
| Automatic failure-rate alert | confirmation attempts + scheduled monitor + system alerts | Phase 5 test |
| Audit cancellation/reissue | append-only audit + ticket reissue endpoint | cancellation + ticket-reissue tests |
| Local metrics/dashboards | Pulse, Horizon, `/api/ops/metrics` | Phase 5 test + local URLs |
| 100x design paragraph | README, DECISIONS, ADR | documentation |
| README and all endpoints documented | `README.md`, `docs/API.md` | static review |
| DECISIONS mandatory answers including AI | `DECISIONS.md` | static review |

## Runtime evidence policy

Files under `docs/evidence/` are generated by the corresponding commands. Do not claim a benchmark or post-infrastructure load-test result that has not been executed on the final code. Before submission run:

```bash
make verify-delivery
```

Then review and commit the regenerated evidence files.
